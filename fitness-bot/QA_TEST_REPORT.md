## 2. КРИТИЧЕСКИЕ БАГИ

### BUG-001: Дублирование обработчика FSM состояния
**Приоритет:** P0 - BLOCKER  
**Файл:** `bot/handlers/food.py`  
**Описание:** Два обработчика с одинаковым декоратором `@router.message(FoodStates.searching_food)` на строках 178 и 702. Второй полностью переопределяет первый.

```python
# Строка 178 - ПЕРЕОПРЕДЕЛЯЕТСЯ (мертвый код)
@router.message(FoodStates.searching_food)
async def process_food_search(message: Message, state: FSMContext):
    ...

# Строка 702 - РАБОТАЕТ (с поддержкой OFF)
@router.message(FoodStates.searching_food)
async def process_food_search(message: Message, state: FSMContext):
    ...
```

**Влияние:** Мертвый код увеличивает сложность поддержки, путает разработчиков. Логика поиска работает только благодаря случайному порядку регистрации роутеров.

**Рекомендация:** Удалить дублирующий обработчик (строки 178-207).

---

### BUG-002: FSM State теряется при перезапуске бота
**Приоритет:** P0 - BLOCKER  
**Файл:** `bot/main.py`, строка 101  
**Описание:** Используется `MemoryStorage()` для хранения FSM состояний. При перезапуске бота все состояния теряются.

```python
storage = MemoryStorage()  # Данные в RAM!
```

**Влияние:** 
- Пользователи теряют прогресс заполнения форм
- При обновлении бота все пользователи в середине процесса получат ошибки
- Невозможно масштабирование на несколько инстансов

**Рекомендация:** Использовать `RedisStorage` для production.

---

### BUG-003: Отсутствует проверка владельца напоминания
**Приоритет:** P1 - CRITICAL  
**Файл:** `bot/handlers/reminders.py`, строка 119-145  
**Описание:** При переключении напоминания не проверяется, принадлежит ли оно текущему пользователю.

```python
@router.callback_query(F.data.startswith("reminder:toggle:"))
async def callback_toggle_reminder(callback: CallbackQuery):
    reminder_id = int(callback.data.split(":")[2])
    # НЕТ ПРОВЕРКИ: reminder.user_id == user.id
    reminder = await reminder_service.toggle_reminder(reminder_id)
```

**Влияние:** Теоретически злоумышленник может манипулировать чужими напоминаниями, перебирая ID.

**Рекомендация:** Добавить проверку в `reminder_service.toggle_reminder(reminder_id, user_id)`.

---

### BUG-004: Отсутствие graceful error handling в OFF интеграции
**Приоритет:** P1 - CRITICAL  
**Файл:** `bot/handlers/food.py`, строки 714-742  
**Описание:** При ошибках API Open Food Facts приложение может упасть или показать некорректное сообщение.

```python
products = await off_client.search_products(query, limit=8)

if not products:
    products = await off_client.search_products_global(query, limit=8)
# Нет обработки исключений на уровне хендлера!
```

**Влияние:** При таймауте или ошибке сети пользователь не получит понятного сообщения.

**Рекомендация:** Обернуть в try-except с user-friendly сообщением об ошибке.

## 3. СЕРЬЕЗНЫЕ БАГИ

### BUG-005: Неверный расчет средних показателей за неделю
**Приоритет:** P2 - MAJOR  
**Файл:** `services/stats_service.py`, строки 74-101  
**Описание:** Метод `get_weekly_averages` использует AVG по записям, а не по дням.

```python
func.avg(FoodEntry.calories).label("avg_calories"),  # Неверно!
```

**Влияние:** Если пользователь добавил 5 записей в понедельник и 1 во вторник, среднее будет искажено (взвешено по количеству записей, а не по дням).

**Рекомендация:** Группировать по дням, затем считать среднее.

---

### BUG-006: Нет валидации отрицательных значений при ручном вводе
**Приоритет:** P2 - MAJOR  
**Файл:** `bot/handlers/food.py`, строки 396-498  
**Описание:** При ручном вводе продукта можно ввести отрицательные значения БЖУ.

```python
# Строка 400
calories = float(message.text.strip().replace(",", "."))
if calories < 0 or calories > 1000:  # Верно для калорий
    ...

# Строка 422 - БЕЗ ПРОВЕРКИ ОТРИЦАТЕЛЬНЫХ!
protein = float(message.text.strip().replace(",", "."))
await state.update_data(custom_protein=protein)  # -100 сохранится!
```

**Влияние:** Некорректные данные в базе, искаженная статистика.

**Рекомендация:** Добавить валидацию `>= 0` для белков, жиров, углеводов.

---

### BUG-007: Нет кнопки "Назад" в процессе онбординга
**Приоритет:** P2 - MAJOR  
**Файл:** `bot/handlers/onboarding.py`  
**Описание:** Пользователь не может вернуться на предыдущий шаг при ошибке.

**Влияние:** Если пользователь случайно ввел неверный пол, он должен пройти весь онбординг заново через /start.

**Рекомендация:** Добавить кнопки "Назад" на каждом шаге онбординга.

---

### BUG-008: Race condition при обновлении streak
**Приоритет:** P2 - MAJOR  
**Файл:** `services/user_service.py`, строки 142-171  
**Описание:** При множественных одновременных запросах возможен race condition.

```python
async def update_streak(self, telegram_id: int) -> User:
    user = await self.get_user_by_telegram_id(telegram_id)  # Read
    # ... логика ...
    user.current_streak += 1  # Modify
    await self.session.commit()  # Write
    # Между Read и Write другой запрос мог изменить данные
```

**Влияние:** Некорректный подсчет серий при высокой нагрузке.

**Рекомендация:** Использовать `SELECT ... FOR UPDATE` или атомарные операции.

---

### BUG-009: Дублирование функции create_progress_bar
**Приоритет:** P2 - MAJOR  
**Файлы:** `bot/handlers/start.py:19`, `bot/handlers/food.py:21`, `bot/handlers/stats.py:18`, `bot/handlers/water.py:20`  
**Описание:** Функция `create_progress_bar` реализована 4 раза с разной логикой!

| Файл | Поведение при 100% |
|------|-------------------|
| start.py | `"▓"*12 + " ⚠️ +X%"` |
| food.py | `"▓"*12 + " ⚠️"` |
| stats.py | `"▓"*10 + " ✅"` |
| water.py | `"💧"*12 + " ✅"` |

**Влияние:** Несогласованный UX, сложность поддержки.

**Рекомендация:** Использовать централизованную функцию из `bot/utils.py`.

---

### BUG-010: Нет пагинации в результатах поиска
**Приоритет:** P2 - MAJOR  
**Файл:** `bot/handlers/food.py`, `services/food_service.py`  
**Описание:** Поиск всегда возвращает максимум 8 результатов без возможности посмотреть больше.

**Влияние:** Пользователь не найдет нужный продукт, если он не в первых 8 результатах.

## 5. ПРОБЛЕМЫ ЮЗАБИЛИТИ (UX)

### UX-001: Длинный процесс ручного ввода продукта
**Серьезность:** Высокая  
**Описание:** Для добавления кастомного продукта нужно ввести 5 значений последовательно (название, калории, белки, жиры, углеводы).

**Текущий flow:**
1. Выбрать прием пищи
2. Нажать "Ввести вручную"
3. Ввести название
4. Ввести калории
5. Ввести белки
6. Ввести жиры
7. Ввести углеводы
8. Выбрать порцию

**Рекомендация:** Разрешить ввод всех данных в одном сообщении:
```
Курица, 165 ккал, 31 Б, 3.6 Ж, 0 У
```

## 6. ПРОБЛЕМЫ БЕЗОПАСНОСТИ

### SEC-001: Отсутствует rate limiting
**Серьезность:** Высокая  
**Описание:** Нет защиты от спама запросов. Пользователь может отправлять неограниченное количество запросов.

**Риск:** DoS атака, повышенная нагрузка на БД и API.

---

### SEC-002: SQL Injection риск в поиске
**Серьезность:** Средняя (смягчено SQLAlchemy)  
**Файл:** `services/food_service.py`, строка 23

```python
Food.name.ilike(f"%{query}%")
```

SQLAlchemy экранирует параметры, но стоит использовать параметризованные запросы явно.

---

### SEC-003: Отсутствует валидация telegram_id
**Серьезность:** Низкая  
**Описание:** Telegram ID принимается как есть без дополнительной проверки.

---

### SEC-004: Debug режим может раскрыть информацию
**Серьезность:** Средняя  
**Файл:** `bot/config.py`

```python
debug: bool = Field(default=False, env="DEBUG")
```

При `DEBUG=True` могут логироваться sensitive данные.
